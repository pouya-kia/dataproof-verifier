# SQL coverage wave 1 — bounded joined-query predicates and grouping

This is an engineering regression record, not a new scientific experiment or a claim of real-world task coverage. It describes the local post-change run against the preserved DataProof-100 ledger; the per-case ledger and raw artifacts remain private pending redistribution review.

The separate, complete finite two-table INNER JOIN workflow now admits a guarded WHERE tree of `AND`, `OR`, `NOT`, `IS [NOT] NULL`, and type-compatible direct-column comparisons, including signed 32-bit INTEGER literals. WHERE retains only SQL TRUE; FALSE and UNKNOWN are filtered. A retained view can group by one or two distinct, alias-qualified direct columns. Projection order follows the declared SELECT list. The one-table Z3 workflow, existing CLI statuses, and Proof2Test target grammar are unchanged. This wave does **not** add STRING, casts, arithmetic, CASE, LEFT JOIN, CTEs, timestamps, windows, dbt compilation, or incremental semantics.

The baseline inventory had 100 identities: 50 public-origin and 50 researcher-authored. The 50 public-origin records were reassessed unchanged: 29 remain `UNSUPPORTED_SQL`, two lack a complete original contract, and 19 are outside the verification obligation or otherwise not applicable. None was executed as a complete original task; **0/50 is the original-task success count**, not an estimate of potential value. The original ledger does not preserve complete SQL/schema/expected-outcome evidence for many public tasks. Newly accepted syntax in a synthetic example must not be counted as a solved original requirement.

Of 50 researcher-authored entries, 34 direct fixtures were re-executed with immutable inputs: 14 NoUndo counterexamples, five NoUndo bounded negatives, six Doppelgänger blind spots, two Doppelgänger bounded negatives, one inconsistent-tests result, three unsupported inputs, and three invalid inputs. The 28 applicable finite-oracle comparisons agreed; 20 positive witnesses passed independent DuckDB replay. There were no observed direct-case status changes or invalid positive replays. Thirteen more authored controls were re-executed: Proof2Test defective/corrected outcomes, duplicate/output-bag controls, dbt export controls, invalid/tampered inputs, artifact ownership, and injected solver-error categories. The dbt YAML was exported but **not** run under dbt Core; the injected reasons are mocks, not real timeouts. A22, A27 and A30 remain inadmissible designs and were not executed. Thus **47/50** authored controls were exercised, not 50 independent successes.

An initial private accounting pass incorrectly mapped Doppelgänger positive oracle status and was superseded, without deleting its record. A first follow-up pass accidentally used an unsupported `ORDER BY` target for A40 and failed. The original A40 control uses the supported corrected target; its repeat passed. The unsupported-target failure is preserved as a harness-selection error, not a product regression. These are post-change engineering controls, not a fresh blind holdout or scientific comparison.

New wave-specific tests compare Python finite evaluation against original SQL executed by DuckDB across every legal world of several small nullable, duplicate-bag and DATE examples; they cover positive and complete bounded-negative results, SQL UNKNOWN, grouping-order and aggregate-order behavior, parser rejection, artifact isolation and serialized replay. The new `examples/join/filtered_fanout.json` is explicitly synthetic. Complete negative claims remain capped by the admitted analytical finite-world bound; timeout and reference disagreement fail closed.

Local validation at the wave-1 working-tree snapshot: full suite **236 passed, one skipped**; focused joined-query suite **40 passed**; Ruff lint/format and mypy passed; Wheel and sdist built. A fresh Python 3.11 Wheel installation ran joined preflight/check/replay successfully outside the source tree. The first install attempt accidentally used the unsupported system Python 3.9 and failed during dependency resolution. On macOS, `pip check` still reports the previously known `z3-solver 5.3.1.0` platform-metadata incompatibility, despite executable Z3-backed tests passing; this must not be represented as a clean dependency audit.

The original `v0.1.0a1` release, frozen Paper 1–3 evidence and historical negative practical gates are unchanged. The new admitted grammar remains too narrow to justify any original-task adoption or performance claim. Further waves require their own source-level gates and complete post-change ledger assessments.
